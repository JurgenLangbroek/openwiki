# Glean's OAuth endpoints are confined to Glean's registrable domain, in code

Glean's OAuth endpoints are all discovered from metadata served by a backend whose host is the most user-supplied one in this system: it is derived from a work email domain, from an instance name typed during setup, or from `OPENWIKI_GLEAN_BACKEND_URL` / a connector-config `backendBaseUrl`, which accept any HTTPS origin. Whatever that resource server names in `authorization_servers` becomes the authorization server, and whatever that server advertises as `token_endpoint` receives the refresh token. The Glean auth provider therefore declares `oauthAllowedHosts: [GLEAN_REGISTRABLE_DOMAIN]` (`glean.com`, one named constant shared with the backend-URL builder so the list and the hosts it must admit cannot drift apart). Upstream's matcher does exact-or-suffix matching, so this admits every instance-derived backend (`acme-be.glean.com`) and any separately-hosted authorization server on the same domain, while refusing anything off it. A Glean deployment on a custom domain must widen the list **in code**, and `resolveOAuthMcpResourceUrl` refuses to resolve at all for a provider that discovers endpoints from metadata and declares no non-empty list, so the next such provider cannot inherit the hole by omission.

**Considered options:** an env-var or connector-config override for the allowed hosts was rejected as self-defeating — it would be read from the same user-supplied surface the list exists to constrain, so anyone who could redirect the backend could also widen the list. Declaring the backend's exact hostname was impossible: it is per-tenant and unknown until setup. Leaving `oauthAllowedHosts` unset (upstream's default) was the status quo and meant the host check was inert for the fork's most user-supplied provider. Expressing the "discovering providers must declare a list" rule as a compile-time assertion over `AUTH_PROVIDERS` was rejected: it requires re-annotating an upstream-exported declaration with `satisfies` to retain per-provider literal types, which changes an upstream symbol's inferred type for a signal that still would not fail closed at runtime.

**Consequences:** a custom-domain Glean tenant fails during OAuth with `MCP protected resource URL host is not allowed.`, which names the cause but not the remedy — the wizard's Glean step is the right place to translate it (#60), and this ADR is the record that the refusal is a decision rather than a bug. Suffix matching means **any** `*.glean.com` host is admitted, including one a Glean tenant could stand up; that is accepted, since such a host is already inside the trust boundary the user chose. The control covers the OAuth control plane only: `resolveGleanTarget()`'s `backendUrl`, `gatewayUrl` and `mcpUrl` still carry the access token to whatever origin the same escape hatch produced, tracked as a separate follow-up and deliberately out of this decision's scope.
